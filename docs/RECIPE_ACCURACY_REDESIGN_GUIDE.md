# Recipe 准确性重设计指导：资源分类、有效期与生成验证闭环

- 日期：2026-10-23。
- 状态：**供接手 Agent 审计并提出重设计方案的指导，不是已经实现的架构。**
- 范围：Youju 如何使用 `xdog-agent` 生成 Recipe，以及如何通过 `xdog-flow` 执行、测试和修复 Recipe。
- 不在范围：产品定位、客户端重设计、全国来源拓展、部署、真实通知、自动报名。

## 0. 给接手 Agent 的任务

先读仓库 `AGENTS.md`、根 README 和本文引用的实际代码。审计现有调用链后，提出一个简单、可实施的重设计方案。
本文中的业务约束应满足；接口名、数据形状及模块拆分是建议，必须结合实际代码重新判断，不能照着示例搭建第二套平台。
若发现建议与代码、材料或其他约束冲突，请在方案中明确指出并给出替代设计，不要掩盖冲突。

本阶段要求交付设计，不等于授权修改生产数据、调用付费模型、升级依赖、重启服务或部署。
不要修改相邻 XDOG 仓库；如认为 SDK 存在缺口，列出最小公开 API 需求和证据。

### 核心目标

1. 正确识别列表、详情、混合页面、附件及招聘业务类型，避免在解析前漏掉真实公告。
2. 可靠判断报名规则和时间有效性：**确认已过期的公告快速解析，允许低完整度；未过期或未能确认过期的公告要求高质量解析。**
3. 不要求每页调用模型。通过通用规则、结构适配、一次性疑难判读、版本缓存和规则改进控制成本。
4. 作者 Agent 得到足够案例与可诊断反馈，生成可泛化的解析器，而不是仅通过少量样本的代码。
5. “执行成功”“契约通过”“语义准确”“候选验收”“业务发布”分开记录，不相互替代。

高质量是结果要求，不是“必须用模型”；可靠脚本同样可以完成高质量解析。
低完整度也不是允许编造、串行条件、绕过安全校验，或把粗解析结果冒充高质量岗位。

## 1. 已发现的实现约束：接手时必须重新核实

以下为本次代码审查发现，不是建议功能的实现声明。文件可能继续变化，交付设计时应标记实际审计版本。

| 现状 | 相关文件 | 需要解决的问题 |
| --- | --- | --- |
| 已有页面角色和业务类型两个维度；已有规则与共享轻量分类器 | `server/src/youju/onboarding/classification.py`、`classification_features.py`、`shared_classifier.py` | 复用现有体系，不重复实现分类框架；审计区域识别及错误排除 |
| `page_shape()` 依赖正文、链接、日期等特征 | `classification_features.py` | 整页导航/推荐可能污染主内容判断，应核实真实失败案例 |
| `_template()` 主要使用材料格式、表头信息 | `classification.py` | 不是可靠的 DOM 结构身份，不能凭其相同复用业务分类 |
| 生成输入通常限制为 1–3 个样本，限制跨多层存在 | `sampling.py`、`recipes.py`、`recipe_service/native_runtime.py` | 不只是调大一个常量，应支持按需案例访问与分批测试 |
| 验证先强制 fast probe 完整通过，才运行实际 workflow | `recipes.py::RecipeAuthor.validate_candidate` | 阻止“脚本不支持、详细模型兜底”的合法路径，诱导样本特化 |
| validity 输出须与宿主 `check_validity()` 的状态/日期及部分元数据一致 | `recipes.py::RecipeRunner.run` 内 `validate_validity` | 来源脚本即使识别新表达，也无法扩展宿主未覆盖的判断 |
| 岗位检查主要是结构、有效期及已识别行覆盖 | `server/src/youju/positions/extraction.py` | 不能证明字段、条件、作用范围及未识别行的语义准确性 |
| 详细提取用宿主固定 `V2_INSTRUCTIONS` | `positions/contracts.py`、`onboarding/recipes.py` | 来源专用语义如何受限地传入详细提取，需要明确 |
| 修复验收主要比较解析成功与岗位数量下限 | `onboarding/repair.py::repair_verdict` | 同数量的字段退化难发现；纠正旧假阳性可能被误判退化 |
| 自动修复和修复样本选择主要以 failed 为入口 | `auto_repair.py`、`repair.py::select_repair_samples` | review 和无报错语义问题如何进入诊断；不能无差别反复重试 |

保留已有不可变 RecipeRevision、固定输入版本、隔离执行、持久会话恢复、候选与发布分离等有价值的机制。
不要把历史实验的规则覆盖率、样本通过率或审计 passed 宣称为准确率。

## 2. 责任边界与整体处理链

```text
已批准来源的抓取与材料版本保存
    ↓
来源结构适配 + 通用页面角色识别
    ├─ 列表区域 → 发现候选链接 → 子资源独立判断
    └─ 详情/附件/混合页面正文 → 业务类型识别
                                 ↓
                         招聘公告及相关变更
                                 ↓
                   报名规则提取 + 作用范围/证据检查
                                 ↓
                       宿主统一计算时间有效性
                    ├─ 确认过期 → 低成本粗解析
                    └─ 其他 → 高质量脚本/详细提取
                                 ↓
                      质量检查、存储、业务准入
```

- `xdog-agent`：作者的工具调用、会话、取消、恢复；不加入招聘领域判断。
- `xdog-flow`：真实节点执行、分支、端口校验、节点追踪；不再造一套执行器。
- Youju 来源处理：抓取授权、材料版本、分类、规则提取、分流、业务准入。
- Youju RecipeService：作者任务、受限工具、案例访问、测试、候选版本与反馈。
- 作者 Agent：从案例诊断、生成或修复适配器；不能修改验收器、预期、权限或自行发布。
- 模型判读：无工具的结构化推断；不持有抓取、代码执行或业务发布权限。

通用语义和时间计算共享；适配差异主要是材料结构。不按站点复制完整分类器、有效期引擎或模型配置。
来源与模板不是同一概念：一个站点可以包含多个结构，不同站点也可以使用相同 CMS。

## 3. 第一部分：资源分类

### 3.1 分开结构和业务，允许混合与未知

结构角色沿用现有契约为优先，区分列表、详情、导航、附件、其他/未知；允许同页包含正文和列表区域。
业务区分招聘、更正/延期、取消、指南、结果通知、新闻报道、无关/未知。延期是否使用已有 correction 细分，接手设计时确定。

- 招聘栏目不等于每条链接都是招聘公告。
- 文章详情不等于招聘公告。
- 含大量链接不等于列表，含招聘关键词不等于招聘意图。
- 错误页、登录页、验证码、空壳和动态未加载页面应显式识别，不能伪装为确定无关。
- 更正/取消要关联目标公告，不能作为普通新增岗位公告直接解析。

### 3.2 区域先于整页统计

尽可能区分主正文、重复条目、导航、推荐区域。组合信号，不用单一链接数/文本长度决定结论：

| 角色 | 可用信号 | 反例 |
| --- | --- | --- |
| 列表 | 同父容器的重复条目、独立目标、对应日期、分页 | 正文中的附件清单、推荐链接 |
| 详情 | 主标题与连续正文、发布元数据、当前文章附件 | 列表摘要、历史文章引用 |
| 招聘意图 | 正文中相互关联的单位/岗位/条件/报名安排 | 招聘工作会议报道、论坛参会报名 |

来源适配可定位区域/字段并声明适用条件，但不得删除必要上下文来制造“确定分类”。
没有清晰 DOM 时允许内容特征和保守弃权，不要求为所有来源强建模板系统。

### 3.3 分层判断和错误处理

1. 资源类型与材料可读性检查。
2. 已验收结构适配与通用规则。
3. 已验证的轻量分类模型（现有模型可复用，但须满足真实数据验收）。
4. 未决、结构异常或规则冲突时，选择性调用通用模型。

规则短路也要评测；不能只测轻量模型，忽略规则先犯错。
未知必须保留待判读状态，模型预算不足不等于确定无关。
列表发现与当前页面业务标签分离：不能仅因页面无关而自动关闭已批准范围内的链接发现。
列表链接继续受现有 SSRF、来源范围、去重、限流和资源上限保护，不允许无限爬取。
混合页可同时发现链接和分析正文，按资源/材料身份去重。

### 3.4 模型和结构复用

模型及核心分类语义全来源共用。AI 可协助辨识新结构，作者据此生成最小适配，测试后启用。
缓存单份材料分类结果与复用结构规则是两回事；不得因模板相同复制某页的业务结论。
结构规则必须有适用检测与失配回退；改版后停止套用旧规则，不按站点标签强判。
不信模型自报置信度。阈值须用独立数据校准，未知是合法结果。

## 4. 第二部分：报名有效期与解析分流

### 4.1 核心不对称性

把未过期公告错判过期，会导致错误降级，代价高于多做一次高质量解析。
因此：**只有充分支持“报名范围已结束”才能走粗解析；无法确认过期不能降级。**
不承诺自然语言判断零错误；用证据、保守弃权、独立验收降低错误降级风险。

分开三件事：原文报名规则、按显式时钟计算的有效期、当前是否仍有招聘名额。
未来截止、长期有效或招满为止，都不能证明当前仍有空缺。保留 `current_hiring_status=not_verified` 等现有边界。

### 4.2 提取与时间计算分离

生成适配器提取“规则及依据”，宿主统一计算是否过期。规则概念至少覆盖：

- 明确截止；开放式/长期；招满为止。
- 相对日期；多轮/多岗位范围；冲突/未声明/无法判断。
- 原文引用、已有材料定位、所属材料版本和作用范围。
- 精度、时区以及必要的可信发布日期/日历依据。

优先扩展/收口已有 `application_period`，不要未经评估再造另一份重复 schema。
以下仅表示语义，不是强制 API：

```json
{
  "kind": "fixed_deadline",
  "deadline": "2026-10-31",
  "precision": "day",
  "timezone": "Asia/Shanghai",
  "scope": "notice",
  "text": "报名截止日期为2026年10月31日",
  "evidence_ids": ["b18"]
}
```

具体字段、时间边界、证据版本与作用范围身份须在正式设计中完整定义。
不能用抓取时间代替发布时间；不能在无依据时补年份。
“工作日”需要明确日历/口径；无法证明时不得按普通天数猜算。
日期级截止通常包含当天；精确时刻按明确时区处理。用注入时钟测试，不依赖运行机器当前日期。

### 4.3 范围与更正优先于时间比较

- 不拿面试、到岗、证书、合同日期作为报名截止。
- 分岗位日期不能用最早日期关闭整份公告。
- 多轮招聘、滚动招聘、例外须保留；不能只提取第一个日期。
- 新更正、延期、取消只有在关联依据成立后才能作用于原公告，不能只按较新发布时间覆盖。
- 关键缺失材料是否会影响结论须显式判断。不能一律因附件缺失抹掉正文明确截止，也不能声称缺失附件无影响。
- 整份公告粗解析需要证明适用招聘范围均已结束；无法划清岗位范围时不做局部降级。
- 取消不是普通时间过期，其发布/展示处理保持独立。

区分“保存材料下推算截止已过”和“最近核实没有延期”。抓取/更正覆盖与检查时效属于外部事实，不能由脚本保证。

### 4.4 低成本识别与缓存

顺序为通用规则 → 已验收来源/结构适配 → 对影响分流的未决案例做一次性模型判读。
不要求每份未知公告都立即调用模型；没有时间依据时可保留 unknown，继续高质量岗位解析。
模型判读只提取规则和依据，不启动代码作者、不改变权限、不直接激活新规则。
相似案例聚合后交给作者改进可复用脚本，不是永远逐页询问同一问题。

缓存键至少考虑材料/附件及已关联更正版本、适配与语义规则版本；模型参与时记录实际配置与版本信息。
时钟变化只重算，不重新提取；材料、更正关联或相关规则变化才触发相应失效。
缓存不能把以前的 unknown 永久锁死，也不能把新材料套用旧日期。

### 4.5 修正现有校验的限制

不得简单删除 `validate_validity`，也不得继续要求所有新适配都复现旧 `check_validity()` 的答案。
改为分层检查：结构和引用有效、报名语义与范围支持、日期转换正确、冲突处理、规则验收案例。
“证据 ID 存在”或“原文出现这个日期”本身不证明它是报名截止。
现有通用规则作为基线/冲突信号，不作为永远正确的唯一 oracle。
新旧规则冲突时保留诊断；未经解决，不允许新规则把潜在有效公告降级。
新增通用能力需独立共享回归和显式启用，作者不能在来源任务中修改运行中的共享解析器。

## 5. 第三部分：Recipe 生成、执行与修复闭环

### 5.1 尽量固定 Flow 骨架，生成最小适配

优先宿主维护并测试的骨架：有效期提取/计算 → 质量分流 → 脚本或详细提取 → 检查/汇总。
Agent 主要修改解析适配器和配置，必要时才修改受限 workflow；不要为了“AI 生成”让每个站重复设计图。
分类适配是否作为独立来源产物、还是与 Recipe 同包，需正式设计说明；不可假装它可由尚未分类的三份公告自动完成。
各部分可分别测试、修复与记录版本；不要求一个站点只有一套结构。
不引入通用插件平台、任意代码导入器或额外编排引擎。

### 5.2 两种质量目标，不共用错误的验收门槛

| 路径 | 要求 |
| --- | --- |
| 确认过期 → 粗解析 | 不要求全字段、全条件准确完整；必须遵守安全、基本契约、真实状态及不编造的约束 |
| 未过期或未确认过期 → 高质量解析 | 在可用材料范围内准确提取岗位及条件；不支持部分显式报告或进入详细提取 |

粗解析可以选择省略无法可靠获得的字段/岗位，并明确粗解析标识；不能因数量少触发与高质量相同的补全循环。
如何用最小变更记录 quality tier，以及如何阻止粗结果冒充高质量结果，正式设计必须明确。
材料缺失是材料状态；脚本不支持是解析能力状态；两者不能都用 partial 含糊表达。
只在 schema 层增加可解释的最小字段，不为所有中间状态建立庞大生命周期枚举。

### 5.3 修正 fast probe

保留 fast parser 的隔离、输出契约和安全测试，但取消“所有样本先完整通过 fast，才准测实际流程”。

- 粗解析路径测试基本安全和诚实输出，不要求全量岗位/条件覆盖。
- 高质量脚本路径按其声明支持的结构验证完整性和准确性。
- 不支持应返回可识别的诊断，让真实 Flow 走详细提取，而不是靠硬编码绕过 probe。
- 高质量最终输出必须验收；不能仅凭脚本自报 success 跳过详细提取。
- 模型/预算不可用时显式未完成或降为有标识的待处理结果，不得冒充高质量完成。

路由信号的具体 schema、宿主检查和 Flow 条件，需通过真实分支测试确定，不伪造 SDK 接口。

### 5.4 作者按需看案例，不把全部材料塞进 prompt

替代固定 1–3 样本作为全部观察范围的设计。三份可以是起始窗口，不是源内质量边界。
建议由 RecipeService 注册受限领域工具，名字仅示意：

- `list_cases`：分页列出结构、格式、既有错误与版本。
- `read_case`：读取授权范围内的已保存材料与必要上下文。
- `test_recipe`：对当前候选的固定摘要执行选定案例，返回真实结果与差异。
- `inspect_failure`：读取有界失败详情、输出与原文定位。

工具只能访问任务绑定的输入与候选，不接受任意路径/URL，不接触生产 DB、凭据、网络或验收预期写入。
复用现有受限文件/测试能力可以达到相同目标时，不必强制新增所有工具。
每次测试绑定候选 digest、案例版本、检查器版本和固定时钟，防止旧测试结果被用于新文件。

### 5.5 案例与预期分离

- 开发案例：作者可反复查看与运行。
- 回归案例：历次已确认缺陷、正确行为及负例积累。
- 冻结验收案例：宿主独立执行，作者不能修改预期；反复暴露用于调试后不再算独立 holdout。
- 来源全量回放：观察实际覆盖、未决与退化，不等于所有结果有标准答案。

真值来自人工确认或独立可验证规则。另一模型输出只能是候选标注/疑点，不能自动当 gold。
初期可选择 30–50 份真实材料建立开发与验收集；这是启动建议，不是准确率保证，也不限制之后规模。
切分需考虑来源、结构家族、近重复内容；同模板复制页不能充当大量独立测试。

### 5.6 反馈要能定位具体差异

每个问题包含案例/版本、阶段、字段或岗位定位、实际输出、预期依据、原文定位以及问题来源。
例如“学历错作学位”“第二岗位用了第一岗位条件”“将面试日期作报名截止”，而非只有 RESULT_INVALID。
保留有界的被拒输出及引用，独立于发布结果；不得再用占位空结果误推模型漏提取。
允许分页取详情，不把全部错误堆进一个工具结果或静默截断关键反馈。
材料问题、分类问题、有效期问题、脚本不支持、模型不确定和基础设施失败分别诊断，不全交给作者重写正则。

### 5.7 验收与修复

候选提交 → 契约/安全 → 对应质量路径测试 → 独立语义案例 → 来源回放 → 业务准入。
作者不能以自评、工具调用成功、候选 accepted 或测试数量代替宿主发布结论。
高质量回归比较岗位对应关系、重复/遗漏、关键字段、条件 ALL/ANY、例外与作用范围，不只比数量。
旧输出是变化基线，不是真值；纠正假岗位可以减少数量，需有依据并记录判定。
相同岗位标题不能作为唯一身份；无法可靠对应时报告歧义，不强行匹配。

review 或语义问题可进入诊断，但只有适配器可修且有案例时才进入代码修复。
材料缺失、权限限制、服务故障不能通过重写 Recipe“修好”。
连续提交没有改善或在案例间反复退化时，保留诊断并结束本次任务，不通过无限重试或放宽验收换取通过。
停止条件是修复进展与外部阻塞，不擅自恢复以前移除的作者全生命周期固定 token/轮次/时长限制。

### 5.8 详细模型的来源说明

通用提取模型与核心提示词共享。必要时允许来源提供受限的结构/术语说明，作为领域数据而非系统指令。
不能指定额外工具/权限/任意模型、关闭校验或改变过期标准。网页材料不能注入此信任层。
说明和配置纳入 Recipe 版本、测试及缓存键；其具体必要性应由失败案例证明，避免先造复杂提示词 DSL。

## 6. 必须覆盖的验收矩阵

| 部分 | 正例/反例与边界 | 必须观察的结果 |
| --- | --- | --- |
| 分类 | 真列表、带推荐的详情、新闻中的招聘词、结果公示、混合首页、空列表、动态失败页 | 公告不被静默排除，辅助区域不污染正文，链接发现受限且可持续 |
| 有效期 | 明确报名截止、面试/证书日期、长期/招满、多轮/分岗位、延期/冲突、相对日期缺基准 | 无支持不能判过期，按范围计算，未知不伪装确定 |
| 时钟 | 截止当天、精确时刻、跨日、明确时区、工作日无日历 | 固定输入下确定性计算，不靠模型重算日期 |
| 粗解析 | 确认过期且复杂结构、可用字段很少、零可识别岗位 | 可诚实不完整，不强制高质量覆盖，不输出虚假确定事实 |
| 高质量 | 表格、正文、附件、同标题多岗位、合并单元格、条件例外/ALL/ANY | 完整流程准确，脚本不支持可正确走模型；无模型时诚实未完成 |
| 改版/缓存 | 同模板不同内容、模板改版、附件替换、更正关联变化、规则升级、仅时钟变化 | 不复制业务标签/日期，正确失效，单纯跨日不重复模型调用 |
| 修复 | 同数量字段退化、纠正多余岗位、修一条破另一条、未改文件重复提交 | 语义回归和版本绑定成立，不靠数量单调或自评通过 |
| 恢复 | 作者跨进程继续、候选测试后改动、取消/持久化失败 | 不使用陈旧验收，不自动重放未确认副作用，失败不发布 |

指标必须按阶段与质量路径分开，报告分母和未知/弃权比例：

- 分类：公告漏判、列表候选链接漏提取、新闻误入岗位解析；同时测完整规则/模型决策链。
- 有效期：**仍适用/未解决的报名范围被错判过期并降级的次数**、截止/范围提取正确性、未知率。
- 高质量：岗位精确率/召回、关键字段正确性、条件逻辑正确性；粗解析不套用同样完整度指标。
- 成本：每个新增/变更材料的分类/判期/提取调用与实际用量、缓存命中、作者修复开销，分别统计。
- 效率：被调用模型前后的未决案例减少情况；不以模型自报 confidence、coverage 或审计 passed 当准确率。

小样本“未发现错误”不证明零错误。数值准入阈值在看到基线和标注支持后提出，不凭空承诺 99% 或固定节省比例。

## 7. 推荐实施顺序（先设计，再执行获准范围）

1. 冻结离线材料与实际代码版本，收集三阶段已确认失败和负例，建立可复现基线。
2. 明确最小数据契约、信任边界、质量路径以及缓存失效，列出旧接口受影响位置。
3. 先修判期扩展受限与 fast probe 强制完整的机制冲突，加入正确分流测试。
4. 改进分类区域适配、未决保留与错误排除；避免在上游丢失公告。
5. 加入作者按需案例/测试访问、细粒度差异和语义回归；复用现有 native session 与 revision。
6. 对同一冻结材料比较旧/新方案；默认无付费模型的测试使用明确 stub，真实实验另获授权并记录成本。
7. 提交迁移/启用方案：旧版本和结果保留，规则/Recipe 显式切换，不静默将历史粗结果升级为高质量。

实施顺序可按代码依赖调整，但不能在缺少基线时宣称准确性提升。
现有依赖版本和官方 Flow skill 名称/资源路径须实际核实，升级不是准确性问题的默认解法。

## 8. 接手 Agent 最终应交付什么

1. **现状审计**：真实调用链、文件/函数、上述约束是否仍成立，区分代码事实与推断。
2. **简化架构**：分类、判期、生成验证的边界，以及哪些复用、修改、删除；不只添加新模块。
3. **关键契约**：结构/业务分类、报名规则与范围、过期分流、质量等级、测试反馈、版本和缓存。
4. **流程说明**：来源接入、日常新材料、未知判读、作者修复、取消/恢复、候选启用。
5. **实际案例走读**：至少覆盖列表、推荐污染详情、延期、分岗位、fast 不支持而 detailed 成功、纠正旧假岗位。
6. **分阶段改动清单**：具体文件与依赖顺序、数据兼容/迁移风险、回滚/启用边界。
7. **验证计划**：数据划分、gold 来源、阶段指标、真实模型成本、失败与未知如何展示。
8. **取舍说明**：无法低成本保证的部分、保守行为、仍需人确认的真值；不承诺无条件自动准确。

最终方案应回答：为什么这次会比“给三份样本、生成正则、数量不减就算修复”更可靠，且不会变成每页都调用 AI。
