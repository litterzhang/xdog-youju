# Recipe 准确性修复实施指导（2026-10-30）

## 1. 任务、范围与已确认决策

供接手 Agent 在现有实现上修复 Recipe 生成与执行闭环，不是重新设计产品，也不是重新搭建解析平台。
本文为实施指导，**不表示以下修复已经完成**。先读取本仓库 AGENTS.md、README 和实际代码，确认当前版本与工作区改动，再实施最小修改。

用户已明确认可现有公告成本路由：

- 保留近似日期、页面年龄等用于 quick / detailed 分流的策略；不要把它继续列为缺陷。
- 不要求所有未知有效期公告都走 detailed，不要求每篇公告调用模型。
- 成本路由标签不等于岗位截止日期、实际过期状态或语义质量结论。
- 不恢复已退役的 validity / quality_tier 等历史执行契约。

本文对上述取舍的说明优先于早期重设计文档中的相反建议。其他历史文档须结合当前代码阅读，不能照旧方案重建已删除机制。

本次重点是四个可验证的问题：

1. 明确要求漏提后，完整性检查仍认为无需补全。
2. 脚本草稿误识别后，模型缺少安全纠错与撤回能力。
3. Recipe 提交验收缺少独立于生成样本的语义回归。
4. 共享 runtime 重审被误当作源码 revision 的再次审核，造成终态冲突。

## 2. 已有证据与解释边界

以下来自 2026-10-30 对代码与本地保存记录的只读审查，不保证代表线上最新状态。接手后应重新定位、复现，不直接操作原数据库。

### 2.1 真实漏提案例

本地保存的“科技成果转化管理”“科研平台管理”岗位截止日期为 2026-10-31。`requirements_text` 有“硕士研究生及以上学历”、两年及以上相关工作经验及专业要求；保存的模型阶段岗位条件为空，最终条件只有通用 `other`，没有相应学历、专业、工作经验类型。

对保存模型草稿执行检查时：

```text
validate_model_draft(draft, script_draft) -> []
completion_issues(draft)                -> []
needs_semantic_completion(draft)        -> False
```

原因入口为 `positions/completeness.py`：仅在正文含结构化要求且 `not conditions` 时报告一类遗漏。公告共同条件与岗位条件合并后，一个无关的 `other` 就可能掩盖仍未提取的要求。

### 2.2 脚本错误难以被纠正

`positions/drafts.py::merge_drafts` 只更新或追加模型返回的岗位，脚本旧岗位未返回仍保留。例如脚本误把“报名方式”当岗位，模型只返回真实岗位，合并后假岗位仍在。

`validate_model_draft` 又禁止同 key 修改脚本标为 `source` 的标题。保留证据的目标正确，但脚本自报 `source` 不能直接视为已经独立核验的真值。

### 2.3 工具可用不等于语义验收已落地

`recipe_service/native_runtime.py` 提交时要求 1–3 个起始 samples，并主要用这些样本调用 `validate_candidate`。案例工具确实存在，但不能由此推断生成 Agent 实际使用了充分的独立案例。

审查记录中，冻结案例目录有 1314 个 cases，当前 Recipe 的三份样本都是 HTML，coverage 还报告 docx/xlsx 与部分模板未覆盖；本地 `semantic_case_labels`、`semantic_audit_checks` 为空。

这些是验收覆盖证据，不是准确率。类似地，岗位 location/headcount unknown 的比例不能直接解释为错误率。

### 2.4 runtime 重审与 revision 决策混淆

本地 pipeline 曾卡在 `audit / blocked / REVISION_ALREADY_REVIEWED`：active 与 candidate 引用同一个 service revision，该 revision 已 accept，后续 runtime 审核失败却又排队 reject 同一个 revision。

入口：

- `onboarding/pipeline.py`：激活路径已有 `same_revision` 分支；审核失败会走 reject。
- `onboarding/recipe_bridge.py::reject_candidate`：未对同 revision 的 runtime 重审作对应区分。
- `recipe_service/lifecycle.py`：阻止覆盖已终态审核的 revision 是正确保护，必须保留。

## 3. 职责边界

| 组件 | 应负责 | 不应负责 |
| --- | --- | --- |
| 成本路由 | 决定投入程度 | 证明岗位已过期或高质量 |
| 来源 Recipe | 页面/附件结构、岗位候选、来源特有提取 | 自报结果全部可信、绕开共享校验 |
| 共享岗位域 | 规范化、作用域、合并、完整性诊断、证据检查 | 为单一站点堆特判、凭关键词补造事实 |
| 模型提取/纠错 | 根据实际材料补全或提出修正 | 凭空删岗位、编造依据、把建议当硬条件 |
| Recipe 作者 Agent | 生成/修复代码，使用案例与反馈 | 用自生成答案充当独立 gold |
| 验收层 | 固定输入下执行、语义对照和回归 | 把运行成功/数量不降等同准确 |
| pipeline / bridge | 分清源码审核与 runtime 验证生命周期 | 反复改写同一个终态 revision |

复用现有 xdog-agent / xdog-flow 公开 API，不复制模型客户端、工具循环、工作流引擎。不要为本次修复升级依赖或修改相邻 xdog 仓库。

## 4. 修复 A：按明确要求检查遗漏，而不是按条件是否非空

### 最小方案

1. 从岗位 `requirements_text` 与适用的公告共同要求中识别**需要检查的要求线索**。
2. 对照已有条件及其作用域、原文依据，发现未覆盖线索。
3. 生成有定位信息的诊断，进入现有补全流程；不要仅给最终结果贴错标签而没有补全路径。
4. 模型补全、草稿合并、最终事实规范化后都使用一致的检查含义，避免某阶段再次丢失条件。

诊断至少能说明岗位、原文字段/引用、疑似遗漏类型、为什么现有条件没有覆盖。优先扩展现有诊断结构，不建立第二套状态系统。

### 必须避免

- 不把“出现学历关键词”直接变成硬性学历事实。
- 不把“硕士优先”解释为“必须硕士”。
- 不因存在一个 education 就认为所有学历语义已经完整，也不因缺某种类型就一律报错。
- 不把公告条件无差别套给每个岗位；处理岗位覆盖、例外、AND/OR 与冲突。
- 没有地点、人数等事实时保留 unknown，不为了完整率补造。
- detailed 允许脚本直接产出完整结果；不要强制每篇 detailed 都调用 AI。

### 最低回归集

- 通用 `other` 已有，但岗位明确学历/专业/经验均漏提：必须产生有针对性的补全诊断。
- 已有学历，经验漏提：不能被非空条件集合掩盖。
- 条件已完整且作用域正确：不重复补全。
- “优先”“可放宽”“满足其一”、岗位专属要求：不能被硬化或串用。
- 材料确实未提供信息：不能误报成需要编造的必填项。
- 真实两例应从可追溯材料制成脱敏 fixture；临时脚本不是正式回归资产。

## 5. 修复 B：允许有证据的纠错，不允许默默覆盖或删除

先判断现有 draft 契约能否表达纠错；如不能，增加最小、显式的纠错提议，避免建立通用编辑框架。

至少区分：

- 补全未知字段。
- 修正已有字段（例如标题）。
- 撤回误识别岗位。

纠错应绑定旧岗位 key / 原值、固定材料版本及可验证的原文定位。校验器检查引用真实存在、版本/key 对得上、操作契约合法；**引用存在本身不证明语义判断正确**，仍应保留判断来源并接受语义回归。

模型未返回某岗位，只表示未返回，不自动解释为删除。提议无依据或有冲突时，保留原结果及待核验诊断；已接受的修正需可追踪旧值与原因，不应让新旧结果同时成为两个岗位。

对 `source` 的处理：保留来源信息，但不能因旧脚本自报 source 而永远禁止有依据的纠错。也不能反过来让模型自报 source 自动胜过旧值。

### 最低回归集

- 假岗位“报名方式”可通过显式、有依据的撤回消除。
- 模型漏返回真实岗位：真实岗位仍保留。
- 标题纠错成功但 key 身份不漂移，不生成重复岗位。
- 无依据、错版本、错 key、冲突纠错：不得静默生效。
- 条件逻辑、证据引用随修正保持有效；失败可诊断。

## 6. 修复 C：生成样本与独立验收分开

不要只把 3 改成更大数字，也不要要求每次跑完全部 1314 个案例。

### 最小闭环

1. 起始 1–3 个样本继续作为作者启动上下文。
2. 复用已有 cases / semantic labels / audit checks 存储与案例工具，补齐实际接线，不平行造新案例库。
3. 建立小而明确的语义回归集：真实失败例、不同已支持格式/模板、作用域和纠错反例。
4. 提交时由验收端运行预先确定的独立集合，不依赖作者声明“我测过”；避免作者自行选择一个更容易的集合。
5. 新失败进入可追溯反馈，并成为后续修复回归；反馈要能定位到输入和字段，而非仅“岗位数偏少”。

独立验收样本不应成为作者可编辑的答案。失败反馈可以提供给修复 Agent，但应区分已用于修复的回归样本与仍未参与调试的留出样本，不把前者成绩宣称为独立泛化表现。

最小标签只记录已核实的事实与依据：材料版本、原文定位、岗位身份、目标字段/条件/作用域、预期或允许的未知/待确认状态。无需给每页标完整答案。另一模型的输出不是天然 gold。

报告分开记录：执行/契约通过、语义检查结果、覆盖格式/模板、模型调用与成本。没有标签的样本只能证明回放兼容，不能纳入“语义准确率”的分母。

现有候选展示策略不在本次修改范围；验收缺口不能通过隐藏不完整岗位来掩盖。

## 7. 修复 D：源码 revision 审核与 runtime 重审分离

沿现有 `same_revision` 处理思路收口，不新建第二套控制面。

- 源码新 revision 的 accept/reject：仍由 recipe service 的不可变终态审核管理。
- 同一源码 revision 在不同 runtime / 配置 / 材料下的重审：记录到对应 audit 与 candidate/binding generation，不再次 accept/reject 同一源码 revision。
- 失败可保留失败 candidate 与反馈并阻止相应激活，但不能篡改已 accepted 的历史。
- 验证结果必须绑定实际影响执行的版本身份，避免旧 audit 对新 candidate/generation 生效。

对已经存在的 pending reject：先提供只读诊断与显式修复方案。不能默认删除队列、重置状态、吞掉 `REVISION_ALREADY_REVIEWED` 或把冲突当成功。

### 最低回归集

- 新 revision 首次 accept / reject 正常，重复同请求幂等，冲突决策仍拒绝。
- 已 accepted 的同 revision runtime 重审失败：保存失败，不发第二个 reject。
- 同 revision runtime 重审通过：不发第二个 accept，按实际 generation 处理激活。
- 迟到审核、重试、并发 generation 变化：不能污染新候选。
- 现有遗留冲突可诊断；修复动作必须显式授权，默认测试不改原库。

## 8. 推荐实施顺序与验证

1. 先把上述失败固化为离线回归；记录修改前实际失败位置。
2. 修复 D，让审核生命周期不再阻断后续闭环。
3. 修复 A，打通漏提诊断至现有补全分支，并验证合并后的结果。
4. 修复 B，通过最小契约支持可追溯纠错。
5. 接入 C 的独立语义验收，用 A/B 真实失败例验证作者反馈链路。

每步说明变更对其他来源的影响。不得在共享模块硬编码 USTC URL、岗位名或来源 ID 来通过案例。

在现有环境运行，具体测试文件随实际改动补充：

```bash
uv run --project server --no-sync pytest \
  server/tests/test_notice_routing.py \
  server/tests/test_position_domain_v3_contract.py \
  server/tests/test_recipe_cases_and_semantics.py \
  server/tests/test_runtime_field_completeness.py -q
```

上述四组在审查时 128 项通过，**同时反例仍成立**；不能把它们全绿当作本次修复完成。还需运行新增回归、bridge/pipeline 生命周期测试，以及按项目配置执行受影响代码的静态检查。

默认验证只用保存材料或合成输入、临时数据库、模拟模型。需要测试模型分支是否被正确调用时，用 mock 断言输入、分支和合并结果；不能因此宣称真实模型已能正确提取。

## 9. 交付与禁止事项

交付至少包含：

- 修改文件、职责边界与契约变化。
- 每个真实失败例修改前/后的具体差异及原文依据。
- 新增回归、原有回归与未验证范围。
- 保持成本路由不变的证据。
- 尚未支持的格式/模板、仍需核验的歧义。
- 若需重跑历史数据，单列有范围、有备份、有回滚方案的后续操作，不混入代码测试。

本指导不授权：写生产数据库、删除/重跑历史岗位、修改现存审核记录、调用付费模型、升级依赖、部署、重启共享服务、发送真实通知。实施过程中不要修改相邻 xdog 仓库，也不要覆盖其他 Agent 的改动。

最终结论必须区分“代码路径已修复”“离线语义回归通过”“真实模型验证”“生产数据已重算”。不得以测试总数或执行成功代替准确性证据。
